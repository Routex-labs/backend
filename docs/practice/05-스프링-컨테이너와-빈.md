# 05. 스프링 컨테이너와 빈

**대응 강의** — 스프링 핵심 원리 기본편 `4. 스프링 컨테이너와 스프링 빈`,
`5. 싱글톤 컨테이너`, `6. 컴포넌트 스캔`, `7. 의존관계 자동 주입`, `9. 빈 스코프`

---

## 1. 생성자 주입 — 예외 없이

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class FloorMapService {

    private final FloorRepository floorRepository;
    private final StoreRepository storeRepository;
    private final PoiRepository poiRepository;
    private final BuildingGeoTransforms geoTransforms;
    private final GraphService graphService;
}
```

`@Autowired` 필드 주입, setter 주입이 코드에 **한 곳도 없다.** 강의 7장의 결론 그대로다.

- 필드가 `final`이라 **누락되면 컴파일이 실패한다.**
- 생성자가 하나뿐이므로 `@Autowired`를 생략할 수 있다(스프링 4.3+). `@RequiredArgsConstructor`
  가 그 생성자를 만든다.
- 테스트에서 `new BuildingService(repo, transforms, revisions)`로 컨테이너 없이 만들 수
  있다. 실제로 `BuildingServiceTest`가 그렇게 한다.

**`@RequiredArgsConstructor`의 함정도 그대로 진다** — 필드 선언 순서가 곧 생성자 인자
순서다. 같은 타입 필드가 둘이면 순서를 바꿔도 컴파일이 통과한다. 여기 서비스들은 타입이
전부 달라서 아직 안 걸렸다.

---

## 2. 싱글톤과 무상태 — 딱 하나 예외가 있다

강의 5장의 규칙: **스프링 빈은 싱글톤이므로 상태를 갖지 마라.**

서비스 6개 중 5개는 필드가 전부 `final` 의존성뿐이다. `TileService`만 다르다.

```java
@Service
@RequiredArgsConstructor
public class TileService {

    private final LoadingCache<TileKey, byte[]> tileCache = Caffeine.newBuilder()
            .maximumWeight(MAX_CACHE_BYTES)
            .weigher((TileKey key, byte[] bytes) -> bytes.length)
            .build(this::render);

    private final LoadingCache<String, Map<String, double[]>> labelMemos = ...;
}
```

**의도적으로 공유하는 상태**다. 싱글톤이어야 캐시가 의미가 있다 — 요청마다 새로 만들면
적중률이 0이다. 지켜야 하는 조건이 둘이고, 둘 다 지켜져 있다.

1. **스레드 안전한 자료구조를 쓴다.** `Caffeine`은 동시 접근을 전제로 만들어졌고, memo
   맵도 `ConcurrentHashMap`이다. 일반 `HashMap`이었다면 동시 요청에서 깨진다.
2. **상한이 있다.** 64MB(`maximumWeight` + `weigher`), memo는 8개. 상한 없는 맵은 오래 사는
   배포 프로세스에서 메모리가 계속 커진다 — 실제로 예전 구현이 그랬다는 게 주석에 있다.

강의 9장의 프로토타입/리퀘스트 스코프는 안 쓴다. **요청별 상태가 필요한 자리가 없다.**

## 3. 컴포넌트 스캔

```java
@SpringBootApplication          // = @ComponentScan + @EnableAutoConfiguration + @Configuration
@ConfigurationPropertiesScan
public class BackendApplication { ... }
```

`spring` 패키지 루트에 있으므로 하위 전부가 스캔 대상이다. 강의의 "설정 클래스를 최상단
패키지에 두고 `basePackages`를 지정하지 않는다"와 같다.

`@ConfigurationPropertiesScan`이 하나 더 붙어 있다 — 아래 5절에서 이야기한다.

수동 등록(`@Configuration` + `@Bean`)은 두 곳뿐이다.

| 클래스 | 왜 수동인가 |
|---|---|
| `CorsConfig` | `WebMvcConfigurer` 구현이라 스프링 MVC 설정 확장점이다 |
| `P6SpyConfiguration` | 빈 후처리기 (아래) |

`TestcontainersConfiguration`도 `@TestConfiguration` + `@Bean`인데, 테스트에서만 올라온다
→ [06](06-스키마와-테스트.md).

## 4. 빈 후처리기(`BeanPostProcessor`)가 실제로 쓰인 자리

강의에서 개념으로만 지나가는 `BeanPostProcessor`가 여기서는 **실제 문제를 푼다.**

```java
@Configuration
@Profile("!prod")
public class P6SpyConfiguration implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        return bean instanceof DataSource dataSource ? new P6DataSource(dataSource) : bean;
    }
}
```

컨테이너에 등록되는 모든 빈을 훑어 **`DataSource`면 프록시로 바꿔치기한다.** 바꿔친
`P6DataSource`가 SQL과 바인딩된 파라미터를 로그로 남긴다.

### 왜 이 방법이어야 했나

p6spy의 보통 사용법은 JDBC URL에 접두사를 붙이는 것이다.

```
jdbc:postgresql://...   →   jdbc:p6spy:postgresql://...
```

**이 저장소에서는 조용히 무시된다.** `spring-boot-docker-compose`와 Testcontainers 지원이
실행 중인 컨테이너를 보고 `JdbcConnectionDetails`를 만들어 `spring.datasource.*`를 통째로
덮어쓰기 때문이다. 실제로 한 번 이걸로 놓쳤다는 게 클래스 주석에 있다.

**DataSource 빈 자체를 감싸면 URL이 어디서 왔든 무관하게 걸린다.** 이게 빈 후처리기를 쓰는
전형적인 이유 — "누가 만들었는지 모르는 빈에 공통 처리를 얹는다"다.

### 스타터를 안 쓴 이유

`gavlyukovskiy`의 p6spy 스프링 부트 스타터가 있고 그걸 쓰면 이 클래스가 필요 없다. 최신
버전이 Boot 4보다 8개월 앞선 빌드라 자동설정 호환이 보장되지 않아서, **본체만 넣고 배선은
직접 했다.** 자동설정 하나를 포기하고 12줄을 얻은 거래다.

## 5. 프로파일

```java
@Profile("!prod")               // P6SpyConfiguration — 운영에서는 아예 빈이 안 만들어진다
```

```java
if (!environment.matchesProfiles("prod")) { ... }   // CorsConfig — 런타임 분기
```

**같은 "운영 여부"인데 방법이 다르다.**

- `P6SpyConfiguration`은 **빈의 존재 자체가 갈린다.** 운영에서는 DataSource를 감싸는 코드가
  실행될 여지가 없다.
- `CorsConfig`는 **하나의 빈 안에서 규칙이 갈린다.** origins 화이트리스트가 있으면 프로파일과
  무관하게 그걸 쓰고, 없을 때만 개발/운영이 갈리기 때문에 조건이 프로파일 하나로 안 잘린다.

p6spy를 운영에서 빼는 건 취향이 아니다 — 요청 하나가 SQL 전문으로 로그 수십 줄을 남기고,
**바인딩된 파라미터가 그대로 찍혀 조회 조건이 로그에 남는다.**

## 6. 외부 설정 — `@ConfigurationProperties` + record

강의는 `@Value`와 `@ConfigurationProperties` 클래스(getter/setter)를 다룬다. 여기서는
**record 생성자 바인딩**을 쓴다.

```java
@ConfigurationProperties(prefix = "navigation.cache")
public record CacheProperties(long tileMaxAge, long tileVersionedMaxAge, long glyphMaxAge) {

    public CacheProperties {
        tileMaxAge = tileMaxAge == 0 ? 60 : tileMaxAge;
        tileVersionedMaxAge = tileVersionedMaxAge == 0 ? 31_536_000 : tileVersionedMaxAge;
        glyphMaxAge = glyphMaxAge == 0 ? 86_400 : glyphMaxAge;
    }
}
```

- **불변이다.** setter가 없으니 런타임에 설정이 바뀔 수 없다.
- **기본값을 compact 생성자에서 준다.** record는 필드 초기화식을 못 쓰므로 방법이 이거다.
  `long`이라 미설정이 `0`으로 들어오고, `0`을 "미설정"으로 해석한다. 캐시 수명이 0인
  설정을 의도할 일이 없어서 성립하는 규칙이다 — **0이 유효한 값인 설정에는 못 쓴다**
  (그때는 `Long` 래퍼 + `null` 검사로 간다).
- **등록은 `@ConfigurationPropertiesScan`**이 한다. `@EnableConfigurationProperties(...)`에
  클래스를 하나씩 적는 대신 스캔으로 두었다. `CorsConfig.CorsProperties`처럼 중첩 record로
  선언한 것까지 자동으로 잡힌다.

값의 출처는 `application.yml`이다.

```yaml
navigation:
  cache:
    tile-max-age: 60
    tile-versioned-max-age: 31536000
    glyph-max-age: 86400
  cors:
    origins: []
```

케밥 케이스 → 카멜 케이스 완화 바인딩(relaxed binding)이 그대로 적용된다.

## 7. `@Bean` 없이 정적 유틸로 둔 것들

`HttpCache`, `PlaceKind`, `SharedPolygons`, `MvtWriter`, `TileBounds`, `AffineFit`,
`PlaceMapper` — 전부 `final class` + `private` 생성자 + `static` 메서드다.

**빈으로 만들지 않은 기준은 "주입할 의존성이 있느냐"다.** 이들은 입력만 받아 출력을 내는
순수 함수라 컨테이너가 관리할 게 없다. 빈으로 만들면 테스트에서 주입이 필요해지고 mock을
넣을 수 있게 되는데, mock을 넣고 싶은 대상이 아니다.

반대로 `BuildingGeoTransforms`·`TileRevisions`는 리포지토리를 읽고 결과를 캐시하므로 빈이다.

## 정리

| 강의 개념 | 이 저장소 |
|---|---|
| 생성자 주입 | 전부. `@RequiredArgsConstructor` + `final` |
| 필드/setter 주입 | 없음 |
| 싱글톤 무상태 | 서비스 5개. `TileService`만 의도적 공유 상태(스레드 안전 + 상한) |
| 컴포넌트 스캔 | `spring` 루트, `basePackages` 미지정 |
| 수동 `@Bean` | `CorsConfig`, `P6SpyConfiguration`, `TestcontainersConfiguration` |
| `BeanPostProcessor` | p6spy가 DataSource를 감싸는 실제 사례 |
| `@Profile` | p6spy는 빈 존재 자체를 가르고, CORS는 런타임 분기 |
| `@ConfigurationProperties` | record 생성자 바인딩 + `@ConfigurationPropertiesScan` |
| `@Value` | 안 씀 |
| 빈 스코프(prototype/request) | 안 씀 |
| `@PostConstruct` / 생명주기 콜백 | 안 씀 — 초기화가 필요한 빈이 없다 |
