# 06. 스키마와 테스트

**대응 강의** — 활용1 `1. 프로젝트 환경설정`, 스프링 입문 `6. 스프링 DB 접근 기술`,
스프링 데이터 JPA `1. 프로젝트 환경설정`

강의와 가장 크게 갈리는 문서다. 강의 예제는 **엔티티가 스키마를 만든다**(`ddl-auto: create`
+ H2 인메모리). 여기는 **스키마가 먼저 있고 엔티티가 거기 맞춘다**.

---

## 1. `ddl-auto: validate` + Flyway

```yaml
spring:
  flyway:
    baseline-on-migrate: true
    baseline-version: 1
  jpa:
    hibernate:
      ddl-auto: validate
```

| | 강의 | 이 저장소 |
|---|---|---|
| 스키마 생성 | Hibernate (`create` / `update`) | Flyway (`V1__init.sql`) |
| 엔티티의 역할 | 스키마의 정의 | 스키마와 **일치하는지 검증**만 |
| 스키마 변경 | 엔티티 고치고 재기동 | 마이그레이션 파일 추가 |

### `validate`가 실제로 잡아 주는 것

기동 시점에 **엔티티와 실제 테이블이 어긋나면 애플리케이션이 뜨지 않는다.** 컬럼 이름
오타, 타입 불일치, 없는 테이블이 전부 여기서 걸린다.

안 보는 것도 있다. **인덱스와 제약 이름은 검증 대상이 아니다.** `V1__init.sql`이
Hibernate가 붙인 난수 FK 이름(`fk4bh9yh92glu96hunm6w31yt7b`)을 사람이 읽는 이름으로 바꿀
수 있었던 근거가 이거다.

### `baseline-on-migrate`가 필요했던 이유

운영 Supabase에는 **이미 테이블이 있다**(`ddl-auto: update`가 만들어 온 것). 그 DB에 V1을
다시 돌리면 "이미 있다"로 터진다. `baseline-on-migrate: true` + `baseline-version: 1`은
"V1은 적용된 것으로 치고 V2부터 돌려라"라는 뜻이다. 빈 DB(테스트 컨테이너)에는 V1부터
그대로 돈다.

### 기동 순서 함정 — `defer-datasource-initialization`

```yaml
spring.jpa.defer-datasource-initialization: false
```

강의에서 `data.sql`을 쓰려면 이걸 **`true`로 켜라**고 배운다. Hibernate가 테이블을
만들기 전에 시드가 돌면 `relation does not exist`가 나기 때문이다.

Flyway를 쓰면 **반대가 된다.** 순서가 `Flyway → Hibernate 검증 → data.sql`이라 미룰 이유가
없어졌고, 켜 두면 **기동이 아예 실패한다** — Flyway와 `entityManagerFactory` 사이에 순환
`depends-on`이 생긴다.

```
Circular depends-on relationship between 'flyway' and 'entityManagerFactory'
```

### Boot 4 의존성 함정 두 개

`build.gradle` 주석에 남아 있다. 둘 다 **조용히 실패**해서 원인을 찾기 어려웠던 것들이다.

```gradle
implementation 'org.springframework.boot:spring-boot-flyway'   // ← 자동설정 모듈
implementation 'org.flywaydb:flyway-core'
runtimeOnly    'org.flywaydb:flyway-database-postgresql'        // ← PG 방언 모듈
```

- **`flyway-database-postgresql`이 없으면** 기동 시
  `No database found to handle jdbc:postgresql`로 죽는다. Flyway 10부터 방언이 본체에서
  분리됐다.
- **`spring-boot-flyway`가 없으면** 마이그레이션이 그냥 실행되지 않는다. 기동은 되고
  `validate`에서 "missing table"로 터진다. Boot 4가 자동설정을 기술별 모듈로 쪼갠 결과다.

## 2. 컬럼 이름 회귀 테스트

`SchemaColumnNamesTest`는 강의에 없는 종류의 테스트다.

```java
@SpringBootTest
@Import(TestcontainersConfiguration.class)
class SchemaColumnNamesTest {

    private static final Map<String, List<String>> EXPECTED_COLUMNS = Map.of(
            "buildings", List.of("area_m2", "footprint_local_m", "id", "name", "perimeter_m"),
            ...);

    @Test
    void columnNamesMatchPythonSchema() {
        EXPECTED_COLUMNS.forEach((table, expected) -> {
            List<String> actual = jdbcTemplate.queryForList(
                    "select column_name from information_schema.columns "
                            + "where table_schema = 'public' and table_name = ? order by column_name",
                    String.class, table);
            assertThat(actual).containsExactlyElementsOf(expected);
        });
    }
}
```

**왜 있나:** Hibernate 네이밍 전략이 끝에 붙은 대문자 앞에 언더바를 넣지 않아
`perimeterM → perimeterm`, `sourceX → sourcex`가 된다([01](01-엔티티-매핑.md) 3절).
이 함정에 세 번 걸렸고, **그중 둘은 응답에 안 나가는 컬럼이라 API 테스트로는 안 잡혔다** —
실데이터를 넣을 때야 드러났다.

배울 점: **테스트는 "응답이 맞나"뿐 아니라 "다른 시스템과의 접점이 맞나"도 지켜야 한다.**
여기서 접점은 파이썬 백엔드가 쓰던 컬럼 이름이다.

`information_schema`를 직접 읽으므로 인메모리 H2로는 이 테스트가 의미가 없다 — 다음 절로
이어진다.

## 3. Testcontainers — H2 대신 진짜 PostgreSQL

```java
@TestConfiguration(proxyBeanMethods = false)
public class TestcontainersConfiguration {

    @Bean
    @ServiceConnection
    PostgreSQLContainer postgresContainer() {
        return new PostgreSQLContainer(DockerImageName.parse("postgres:18"));
    }
}
```

강의(활용1)는 테스트에 H2 인메모리를 쓴다. 빠르고 설정이 없다. 여기서 못 쓰는 이유:

| 필요한 것 | H2로 되나 |
|---|---|
| `jsonb` 컬럼 (`@JdbcTypeCode(SqlTypes.JSON)`) | 호환 모드로 흉내는 나지만 동작이 다르다 |
| `information_schema` 컬럼 이름 검증 | H2의 결과는 PostgreSQL과 다르다 |
| Flyway `V1__init.sql` (PG 문법) | 안 된다 |
| 운영과 같은 타입 승격·정렬 규칙 | 안 된다 |

**"테스트가 통과하는데 운영에서 깨지는" 종류를 원천 차단**하는 대신, 테스트가 Docker를
요구하고 느려진다. 이식 프로젝트에서는 남는 거래였다.

### `@ServiceConnection`이 하는 일

컨테이너가 뜬 뒤 그 컨테이너의 host/port/유저/비밀번호를 읽어 `spring.datasource.*`를
**자동으로 주입한다.** 예전 방식(`@DynamicPropertySource`로 손수 매핑)이 필요 없다.

이게 [05](05-스프링-컨테이너와-빈.md)의 p6spy 이야기와 이어진다 — 접속 정보가 이렇게
런타임에 덮어써지기 때문에 JDBC URL에 `jdbc:p6spy:`를 적는 방식이 조용히 무시된다.

`compose.yaml`과 **같은 메이저(18)로 맞춘 것**도 의도다. 개발과 테스트가 다른 DB 버전을
쓰면 재현이 안 되는 버그가 생긴다.

## 4. 테스트 전략 — `@DataJpaTest`가 없다

테스트 15개 중 DB를 쓰는 것은 전부 `@SpringBootTest` + `@AutoConfigureMockMvc`다.

```java
@SpringBootTest
@AutoConfigureMockMvc
@Import(TestcontainersConfiguration.class)
class BuildingControllerTest {
    @Autowired private MockMvc mockMvc;
```

**`@DataJpaTest`(JPA 슬라이스 테스트)를 하나도 안 쓴다.** 리포지토리를 따로 검증하지
않는다는 뜻이다.

### 왜 이렇게 했나

리포지토리 메서드가 거의 다 **한 줄짜리 조회**다. 따로 테스트하면 "스프링 데이터 JPA가
제대로 동작하는지"를 검증하게 되지, 우리 로직을 검증하는 게 아니다. 대신 **API 응답을
검사하면 그 경로에 있는 리포지토리가 전부 함께 검증된다.**

### 대가

- 테스트가 느리다(컨테이너 기동 + 전체 컨텍스트).
- 실패했을 때 **어디가 깨졌는지 좁혀지지 않는다.**
- 쿼리 개수(N+1)를 테스트로 못 잡는다. 지금은 p6spy 로그를 눈으로 보는 것이 유일한 방법이다.

`@DataJpaTest`가 정말 필요해지는 시점은 **복잡한 JPQL이 늘어날 때**다. 지금은
`EdgeRepository.findTransferEdges`(양 끝 노드 검사)가 그런 후보인데, `GraphControllerTest`가
응답에 dangling 간선이 없는지로 대신 지키고 있다.

### 순수 단위 테스트는 따로 있다

DB가 필요 없는 것은 스프링 없이 돈다. `AffineFitTest`, `LabelPointTest`, `TileBoundsTest`,
`QueryRankingTest`, `BuildingServiceTest`, `GraphServiceTest`.

**계산 로직을 정적 메서드로 뽑아 둔 덕**이다 — `BuildingService.sortedFloors`,
`defaultFloor`, `GraphService.verticalAllows`가 전부 `static`이라 컨테이너 없이 부를 수
있다.

## 5. `data.sql` 시드가 테스트 설계의 일부다

```sql
-- 일부러 뒤섞어 넣는다. 응답이 level 내림차순(2F,1F,B1)으로 나오는지 보려면
-- 삽입 순서와 기대 순서가 달라야 한다.
INSERT INTO floors (...) VALUES ('ths-1f', ..., 1, ...), ('ths-b1', ..., -1, ...), ('ths-2f', ..., 2, ...)
```

```sql
-- 1F만 자기 외곽선을 갖는다. 나머지 층은 건물 대표 외곽으로 폴백하는 경로를 확인하려고
-- 일부러 비워 둔다.
```

시드가 "그냥 아무 데이터"가 아니라 **각 행이 검증할 분기를 담고 있다.** 삽입 순서를
정렬 기대와 다르게 두지 않으면 정렬 코드를 지워도 테스트가 통과한다.

`ON CONFLICT (id) DO NOTHING`이 붙어 있어 `sql.init.mode: always`로 매 기동마다 돌아도
안전하다.

### 인코딩

```yaml
spring.sql.init.encoding: UTF-8
```

지정하지 않으면 Windows 기본 코드페이지(CP949)로 읽어 **"더현대 서울"이 mojibake로
들어간다.** 실제로 한 번 그렇게 됐고, 그래서 `BuildingControllerTest`가 한글 이름을 직접
검사한다.

```java
// 한글이 깨지지 않는지 본다. data.sql을 CP949로 읽어 한 번 깨졌다.
.andExpect(jsonPath("$[0].name").value("더현대 서울"))
```

같은 이유로 `build.gradle`이 컴파일·테스트 인코딩을 UTF-8로 고정한다.

## 6. 쿼리를 눈으로 확인하는 법 (실습용)

강의가 "SQL을 봐라"고 할 때 쓰는 `show-sql: true`는 여기 없다. 대신 p6spy가 **바인딩된
파라미터까지 값으로** 찍어 준다.

```
1. bootRun (개발 프로파일 — prod가 아니면 p6spy가 걸린다)
2. curl http://localhost:8080/buildings
3. 로그에서 실행된 SQL 줄 수를 센다
```

`spy.properties`가 `commit`·`rollback`·`resultset`을 걸러 두어 **실행된 문장만** 남는다.

확인해 볼 만한 것:

| 요청 | 기대 |
|---|---|
| `GET /buildings` | `buildings` + `floors`가 **한 방에** (left join) — `@EntityGraph` |
| `GET /buildings/{id}/floors/1F` | 층·매장·POI·노드·간선 = 5줄 고정, 매장 수와 무관 |
| `GET /buildings/{id}/graph` | 5줄 안팎. 간선 수에 비례해 늘면 1차 캐시가 깨진 것 |
| `GET .../floors/B1` (외곽선 없는 층) | `buildings` 조회가 한 줄 더 — 프록시 초기화 |

마지막 줄이 [02](02-영속성-컨텍스트와-지연로딩.md)에서 말한 유일한 프록시 초기화 지점이다.
