# 03. 조회 최적화와 N+1

**대응 강의** — 활용2 `3. 지연 로딩과 조회 성능 최적화`, `4. 컬렉션 조회 최적화`,
JPA 기본편 `10. 객체지향 쿼리 언어`

강의 활용2의 핵심 흐름은 **엔티티 조회 → fetch join → DTO 직접 조회 → 필요하면 네이티브**
순서로 내려가면서 상황에 맞는 지점을 고르는 것이다. 이 저장소는 화면마다 다른 지점에
멈춰 있고, **각각 왜 거기서 멈췄는지**가 이 문서다.

| 화면 | 쓴 방법 | 파일 |
|---|---|---|
| 건물 목록·상세 | 엔티티 + `@EntityGraph` | `BuildingRepository` |
| 장소 상세 | 엔티티 + `@EntityGraph` (2단계) | `StoreRepository.findById` |
| 층 지도 / 타일 | 엔티티, 조회 3~4번을 그냥 나눔 | `FloorMapService`, `TileService` |
| 카테고리 pill | **투영**(`Object[]`) + GROUP BY | `CategoryQueryRepository` |
| 자동완성 색인 | **투영**(`Object[]`) | `CategoryQueryRepository` |
| 자연어 질의 | **DTO 직접 조회**(`new` 연산) | `QuerySearchRepository` |

---

## 1. `@EntityGraph` — 컬렉션 N+1을 막은 자리

```java
public interface BuildingRepository extends JpaRepository<Building, String> {

    @Override
    @EntityGraph(attributePaths = "floors")
    List<Building> findAll();

    @Override
    @EntityGraph(attributePaths = "floors")
    Optional<Building> findById(String id);
}
```

**`JpaRepository`의 기본 메서드를 오버라이드해서 애노테이션만 붙이는** 기법이다(스프링
데이터 JPA 강의 5장). 구현은 그대로 두고 페치 계획만 바꾼다.

없으면 건물 목록 조회에서 `buildings` 1번 + 건물 수만큼 `floors` 조회가 나간다. 응답
(`BuildingSummaryResponse`)이 **언제나** 층 목록을 포함하므로 지연로딩으로 둘 이유가 없다.

### fetch join과 뭐가 다른가

`@EntityGraph`는 JPQL을 안 건드리고 페치 계획만 얹는다. 실제로는 **left outer join**으로
나가고, fetch join(`join fetch`)은 기본이 inner join이다. 여기서는 층이 없는 건물도 목록에
나와야 하므로 outer가 맞다 — fetch join을 썼다면 `left join fetch`라고 직접 적어야 했다.

### 강의가 경고한 "컬렉션 fetch join + 페이징" 문제는?

컬렉션을 조인하면 행이 뻥튀기되어 DB 레벨 페이징이 불가능하고, Hibernate가 전부 읽어
메모리에서 자르는(`firstResult/maxResults specified with collection fetch; applying in
memory`) 그 문제다.

**해당 없다.** `findAll()`에 페이징을 안 건다. 건물이 사실상 하나(더현대 서울)라 목록이
페이징될 규모가 아니다. 건물이 수백 개가 되는 날 이 결정이 먼저 깨진다 — 그때 강의의
답(`default_batch_fetch_size` + 컬렉션은 지연로딩)으로 간다.

### 그래서 `default_batch_fetch_size`도 안 켰다

`application.yml`에 없다. 지연로딩으로 남긴 컬렉션이 하나도 없어서 켤 대상이 없다.

### 2단계 경로도 된다

```java
// StoreRepository — 상세는 층 라벨과 소속 건물까지 필요하다
@Override
@EntityGraph(attributePaths = {"floor", "floor.building"})
Optional<Store> findById(String id);
```

이게 있어서 `PlaceDetailService`가 아래를 쿼리 없이 할 수 있다.

```java
.filter(store -> store.getFloor() != null
        && store.getFloor().getBuilding().getId().equals(buildingId))
```

`floor.building`을 안 넣었다면 이 `getId()` 하나 때문에 `buildings` 조회가 더 나간다
(프록시 초기화 — [02](02-영속성-컨텍스트와-지연로딩.md) 참고).

## 2. DTO 직접 조회 — 여기가 이 저장소에서 제일 큰 최적화

```java
// QuerySearchRepository
@Query("""
        select new spring.search.service.StoreRow(
                 s.id, s.name, s.category, s.subcategory,
                 s.centroidXM, s.centroidYM, s.entranceNodeId, s.searchFacets,
                 f.id, f.name, f.level)
          from Store s join s.floor f
         where f.building.id = :buildingId
        """)
List<StoreRow> findAllByBuilding(@Param("buildingId") String buildingId);
```

강의의 "JPA에서 DTO로 바로 조회"(`select new 패키지.DTO(...)`) 그대로다. 여기서 이게 단순
최적화가 아니라 **기능이 성립하느냐 마느냐**인 이유는 `StoreRow`의 주석에 있다.

> 매칭은 이름·분류·facet만 보는데 `select Store`로 읽으면 폴리곤 JSON까지 꺼내 파싱한 뒤
> 버린다 — 파이썬 실측으로 매장 1,640건에서 그 역직렬화가 **235초 중 180초**였다
> (랭킹 자체는 5.7초).

**이 프로젝트에서 "엔티티를 통째로 읽는 비용"이 큰 이유는 jsonb 컬럼 때문이다.**
`Store.polygon`은 좌표 수십 개짜리 JSON이고, `@JdbcTypeCode(SqlTypes.JSON)` 필드는
지연로딩이 아니라 조회 즉시 역직렬화된다. 응답에 안 나가도 비용은 그대로 든다.

일반적인 강의 예제(모든 컬럼이 스칼라)에서는 "DTO 조회는 조금 빠르지만 재사용성이
떨어진다" 정도의 트레이드오프다. 여기서는 **읽는 컬럼을 고르는 것이 곧 성능**이다.

### 생성자 표현식을 쓸 때 실제로 걸리는 것

- 패키지까지 **전체 경로**를 적어야 한다(`new spring.search.service.StoreRow(...)`).
  리팩터링으로 패키지를 옮기면 IDE가 못 따라오고 **런타임에 터진다.**
- 생성자 인자 순서·타입이 정확히 맞아야 한다. `StoreRow`는 인자가 11개고 `String`이
  연달아 있어서 순서를 바꿔도 컴파일은 통과한다.
- `s.searchFacets`처럼 jsonb 필드도 그대로 담을 수 있다. 이건 실제로 필요해서 넣은
  것이라 예외다 — 매칭이 facet을 본다.

## 3. `Object[]` 투영 — DTO 조회의 한 단계 아래

```java
// CategoryQueryRepository
@Query("""
        select f.name, s.category, s.subcategory, count(s.id)
          from Store s join s.floor f
         where f.building.id = :buildingId and s.category is not null
         group by f.name, s.category, s.subcategory
         order by f.name, s.category, s.subcategory
        """)
List<Object[]> countByFloorAndCategory(@Param("buildingId") String buildingId);
```

서비스가 캐스팅해서 받는다.

```java
.map(row -> new CategoryCountResponse((String) row[0], (String) row[1], (String) row[2], (Long) row[3]))
```

**`new` 연산을 안 쓴 값은 얻은 게 없다.** `CategoryCountResponse`는 생성자 시그니처가
그대로 맞으니 `select new spring.category.dto.CategoryCountResponse(...)`로 바꾸면 캐스팅
4줄이 사라진다. 지금 이대로 두는 유일한 이유는 **JPQL이 DTO 패키지를 문자열로 알게
되는 게 싫어서**인데(위의 리팩터링 함정), 이미 `QuerySearchRepository`가 그렇게 하고
있으므로 일관되지는 않다. 고칠 만한 자리로 적어 둔다.

### 여기서도 GROUP BY가 응답 크기를 정한다

pill 화면은 "층·대분류·소분류별 매장 수"만 필요하다. 매장을 전부 읽어 자바에서
`Collectors.groupingBy`로 세면 1,640행이 오가고, GROUP BY로 접으면 **조합 수(실데이터
150행 안팎)로 고정된다.** DB가 할 줄 아는 집계를 애플리케이션으로 가져오지 않는다.

### 정렬을 JPQL에 명시하는 이유

```
order by f.level desc, s.id
```

빼도 결과 집합은 같다. 그런데 **DB 반환 순서에 의존하게 되어 호출마다 순서가 달라질 수
있고**, 클라이언트가 자동완성 색인을 캐시할 때 "내용은 같은데 다른 응답"으로 보인다.
`f.level desc`는 엘리베이터 버튼판 순서고, `s.id`는 PK라 층 안에서 동점이 없다 — 두
키로 전순서가 정해진다.

## 4. 일부러 최적화하지 않은 자리

### 층 지도: 조회 3번을 그냥 나눠 둔다

```java
// FloorMapService.toResponse
List<Store> stores = storeRepository.findByFloorId(floor.getId());
...
graphService.toFloorGraph(floor)                      // nodes 1번 + edges 1번
poiRepository.findByFloorId(floor.getId())            // pois 1번
```

층 하나 + 매장 + POI + 노드 + 간선 = **조회 5번**이다. 한 방에 조인할 수도 있지만
안 한다.

- N+1이 아니다. 데이터 건수와 무관하게 **5번으로 고정**이다.
- 조인하면 매장 × 노드 × 간선의 곱집합이 되어 행이 폭발한다. 서로 관계가 없는 목록들이라
  한 쿼리로 묶을 이유가 없다.

강의의 "쿼리를 줄여라"는 **N에 비례해 늘어나는 쿼리**를 줄이라는 말이지 상수 개를 1로
만들라는 말이 아니다.

### 타일도 같은 구조 + 결과 캐시

`TileService.render`가 층·매장·POI를 읽는다(3번). 대신 **완성된 타일 바이트를 Caffeine에
캐시**해서 같은 좌표의 재요청은 DB에 닿지도 않는다. 캐시 키에 리비전이 들어 있어
데이터가 바뀌면 키가 통째로 달라진다.

엔티티 2차 캐시(`@Cacheable`) 대신 산출물을 캐시하는 쪽을 골랐다 — 적중했을 때 하는 일이
"직렬화 + MVT 인코딩"까지 통째로 사라진다.

### 매장 이름 검색: 인덱스를 못 탄다는 걸 알고 둔다

```java
@Query("select s from Store s where s.floor.building.id = :buildingId and s.name like %:query%")
List<Store> searchByBuildingIdAndName(...);
```

`like '%...%'`는 앞에 와일드카드가 있어 `idx_stores_name`(B-tree)을 못 쓴다. 건물 하나의
매장이 1,640건이라 풀스캔이어도 밀리초 단위라 그냥 둔다. 데이터가 커지면
PostgreSQL `pg_trgm` GIN 인덱스나 전문 검색으로 간다.

여기는 **엔티티를 통째로 읽는다** — 결과가 `StoreResponse`로 나가는데 폴리곤이 응답에
포함되기 때문이다. 위 `StoreRow` 이야기와 반대 방향인데, 폴리곤이 실제로 필요한
화면이라 맞다.

## 5. 강의에 나오지만 여기서는 필요 없던 것

| 기법 | 왜 안 썼나 |
|---|---|
| `distinct` (컬렉션 조인 중복 제거) | 컬렉션 조인이 `Building.floors` 하나고, Hibernate 6부터 엔티티 쿼리는 기본으로 중복을 제거한다 |
| `@BatchSize` / `default_batch_fetch_size` | 지연로딩으로 남긴 컬렉션이 없다 |
| OSIV 끄고 별도 조회 전용 서비스 분리 | 조회 전용 리포지토리(`CategoryQueryRepository`·`QuerySearchRepository`)를 따로 둔 것으로 대신했다 → [04](04-스프링-데이터-JPA.md) |
| 네이티브 쿼리 | JPQL로 다 됐다. jsonb 연산자(`->>`)가 필요해지면 그때 내려간다 |
| Querydsl | 동적 조건이 없다. 질의 조건이 전부 고정이라 문자열 JPQL로 충분하다 |
