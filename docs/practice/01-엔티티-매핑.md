# 01. 엔티티 매핑

**대응 강의** — JPA 기본편 `04. 엔티티 매핑`, `05. 연관관계 매핑 기초`,
`06. 다양한 연관관계 매핑`, `09. 값 타입`

## 1. 기본 매핑

### 적용된 것

```java
@Entity
@Table(name = "buildings")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@AllArgsConstructor
public class Building { ... }
```

여섯 엔티티가 전부 같은 조합이다.

- **`@NoArgsConstructor(access = PROTECTED)`** — 강의 그대로다. JPA 스펙이 기본 생성자를
  요구하는데, `private`으로 막으면 Hibernate가 프록시 클래스(엔티티를 상속한다)를 만들 수
  없다. 그래서 `protected`가 하한선이다.
- **setter가 없다** — `@Getter`만 있고 `@Setter`가 없다. 강의의 "엔티티에 setter를 열지
  말라"와 같다. 여기서는 지킬 이유가 하나 더 있다: 이 서버는 애초에 쓰기를 하지 않아서
  setter가 있으면 **변경 감지로 조용히 UPDATE가 나갈 위험만 생긴다**.

### 강의와 다른 것: `@GeneratedValue`가 하나도 없다

강의는 `@Id @GeneratedValue Long id`가 기본이고 "PK는 대체키(auto increment)를 쓰라"고
한다. 이 저장소는 **전부 `String` 직접 할당**이다.

```java
@Id
private String id;          // 예: "thehyundai-seoul", "FL-xxxx", "{floor_id}:{원본id}"
```

되는 이유는 이 서버가 데이터를 만들지 않기 때문이다. id는 원천 데이터(다비오 스튜디오)가
이미 갖고 있고, 적재는 `tools/load_real_data.py`가 한다. 서버가 생성할 id가 없으니 생성
전략도 필요 없다.

대신 강의가 경고한 비용은 그대로 진다 — **PK가 varchar(255)라 인덱스가 크다.** 실데이터
규모(매장 1,640건)에서는 문제가 아니라 감수했다.

### 강의와 다른 것: `@AllArgsConstructor`를 쓴다

강의는 생성자를 막고 정적 팩토리나 빌더로 만들라고 한다. 여기는 `@AllArgsConstructor`를
그냥 열어 뒀다.

**애플리케이션이 엔티티를 만들지 않아서다.** 인스턴스가 생기는 경로는 두 개뿐이다.

1. Hibernate가 조회 결과로 만든다 → `protected` 기본 생성자를 쓴다.
2. 테스트가 픽스처를 만든다 → 전체 인자 생성자를 쓴다.

"생성 규칙을 강제할 도메인 로직"이 없으니 팩토리를 둘 대상이 없다. 다만 필드가 늘어나면
인자 순서를 틀리기 쉬운 형태이긴 하다(같은 타입 `Double`이 나란히 붙어 있는
`Node.lat/lng/sourceX/sourceY`가 그 예다).

## 2. 연관관계

### 실제 연관 지도

```
Building ─1:N─ Floor          ← 유일한 양방향
                 ↑ N:1
                 ├── Store
                 ├── Poi
                 ├── Node
                 └── Edge (floor_id nullable)

Edge ─N:1─ Node (fromNode)
Edge ─N:1─ Node (toNode)
```

### 적용된 것: `@ManyToOne`은 전부 `LAZY`

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "building_id", nullable = false)
private Building building;
```

강의의 "`@ManyToOne`·`@OneToOne`의 기본값은 EAGER이므로 **반드시** LAZY로 바꿔라"를
예외 없이 적용했다. 여기서 특히 중요한 건 `Edge`다 — 간선 하나가 `floor`·`fromNode`·
`toNode` 3개의 `@ManyToOne`을 갖는데, EAGER면 층 그래프 조회(간선 수백 개)가 즉시 조인
3개짜리 괴물이 된다.

### 적용된 것: 양방향은 하나뿐, 주인은 FK를 가진 쪽

```java
// Building
@OneToMany(mappedBy = "building")
private List<Floor> floors = new ArrayList<>();
```

`floors.building_id`가 FK이므로 **연관관계의 주인은 `Floor.building`**이고
`Building.floors`는 `mappedBy`가 붙은 읽기 전용 거울이다. 강의 05장의 규칙 그대로다.

`Store`·`Poi`·`Node`·`Edge`는 전부 **단방향** `@ManyToOne`이다. `Floor`에
`@OneToMany List<Store>`를 두지 않았다. 강의의 "단방향으로 시작하고 정말 필요할 때만
양방향을 추가하라"를 따랐고, 실제로 필요해지지 않았다 — 층의 매장이 필요한 자리는 전부
`storeRepository.findByFloorId(...)`로 푼다.

`Building.floors`만 양방향인 이유는 **응답이 항상 층 목록을 포함해서**다
(`GET /buildings`, `GET /buildings/{id}`). 리포지토리를 한 번 더 부르는 대신 `@EntityGraph`
한 줄로 같이 읽는다 → [03](03-조회-최적화와-N+1.md).

### 강의와 다른 것: 연관관계 편의 메서드가 없다

강의는 `building.addFloor(floor)`처럼 양쪽을 함께 세팅하는 메서드를 반드시 두라고 한다.
여기엔 없다. **양쪽을 세팅할 코드 자체가 없어서다** — 객체를 만들어 저장하는 경로가
없으므로 "한쪽만 세팅해서 DB와 메모리가 어긋나는" 상황이 생기지 않는다.

쓰기를 한 줄이라도 추가하는 날 이 결정이 먼저 깨진다. 그때 편의 메서드를 넣는다.

### 강의와 다른 것: 연관 대신 문자열 id로 든 자리

```java
// Store
private String entranceNodeId;   // Node를 가리키지만 @ManyToOne이 아니다
// Poi
private String linkedNodeId;     // 같다
```

강의라면 `@ManyToOne Node entranceNode`로 매핑할 자리다. 문자열로 둔 이유:

1. **응답에 나가는 건 id뿐이다.** 클라이언트가 이 id로 온디바이스 다익스트라의 도착점을
   잡는다. 노드의 다른 필드는 한 번도 안 쓴다.
2. **적재 순서 제약을 만들고 싶지 않았다.** 연관으로 매핑하면 FK 제약이 생겨
   `stores`보다 `nodes`가 먼저 들어가야 한다. `V1__init.sql`에 이 두 컬럼만 FK가 없는
   것이 그 흔적이다(파이썬 스키마에는 있다).

대가는 **참조 무결성을 DB가 안 지켜 준다**는 것. 지금은 `tools/load_real_data.py`가
순서를 지키는 것으로 대신한다.

### 강의에 없는 것: nullable한 `@ManyToOne`

```java
// Edge — 층을 잇는 수직 전이 간선은 특정 층에 속하지 않는다
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "floor_id")      // nullable = false 를 못 붙인다
private Floor floor;
```

이 null이 그냥 "값이 없음"이 아니라 **질의 조건으로 쓰인다.**

```java
// EdgeRepository
@Query("select e from Edge e where e.floor is null and ...")
List<Edge> findTransferEdges(...);
```

층별 조회(`findByFloorId`)에서는 자동으로 빠지고, 건물 전체 그래프에서만 합류한다.
"null이 도메인 의미를 갖는" 형태라 `optional = false`나 `nullable = false`를 붙이면
안 된다.

## 3. 컬럼 매핑

### 이 저장소가 세 번 걸린 함정: Hibernate 네이밍 전략

**Hibernate의 기본 네이밍 전략은 끝에 붙은 대문자 앞에 언더바를 넣지 않는다.**

| 필드 | Hibernate가 만드는 컬럼 | 원하는 컬럼 |
|---|---|---|
| `perimeterM` | `perimeterm` ❌ | `perimeter_m` |
| `sourceX` | `sourcex` ❌ | `source_x` |
| `centroidXM` | `centroid_xm` ❌ | `centroid_x_m` |
| `areaM2` | `area_m2` ✅ | `area_m2` |

`areaM2`만 정상인 건 뒤에 숫자가 붙어서다. 그래서 이런 필드에만 `@Column(name = ...)`을
명시한다.

```java
@Column(name = "perimeter_m")
private Double perimeterM;
```

강의는 `ddl-auto: create`라 Hibernate가 만든 이름이 곧 정답이므로 이 함정이 드러나지
않는다. 이 저장소는 **파이썬이 쓰던 테이블에 붙어야 해서** 이름이 하나만 틀려도 적재가
깨진다. 응답에 안 나가는 컬럼(`source_x`)은 다른 테스트로도 안 잡혀서, 회귀 테스트를
따로 뒀다 → `SchemaColumnNamesTest`, [06](06-스키마와-테스트.md).

### 강의와 다른 것: `@Index`·`@UniqueConstraint`는 문서일 뿐이다

```java
@Table(
    name = "stores",
    indexes = {@Index(name = "idx_stores_floor", columnList = "floor_id"), ...})
```

강의에서는 이 애노테이션이 실제로 인덱스를 만든다(`ddl-auto: create`). **여기서는 아무것도
만들지 않는다.** 스키마는 Flyway(`V1__init.sql`)가 만들고 `ddl-auto: validate`는 인덱스를
검증 대상으로 보지도 않는다.

그래도 적어 두는 이유는 **엔티티만 보고도 조회 패턴을 알 수 있게 하려고**다. 다만 이건
"두 곳에 같은 사실을 적는" 상태이므로, 인덱스를 추가할 때 마이그레이션과 애노테이션을
같이 고쳐야 한다.

`floors`의 유니크 제약은 성격이 다르다 — 이건 **다른 코드가 근거로 삼는 약속**이다.

```java
@UniqueConstraint(name = "uq_floors_building_name", columnNames = {"building_id", "name"})
```

건물 안에서 층 라벨("B2")이 유일하기 때문에 API가 내부 id 대신 라벨을 받을 수 있다
(`GET /buildings/{id}/floors/B2`, `QuerySearchRepository.findByBuildingAndFloor`의
`floorKey`).

## 4. 값 타입 — 강의의 결론을 안 따른 자리

**강의 09장의 결론**: 값 타입 컬렉션(`@ElementCollection`)은 실무에서 쓰지 마라. 변경 시
전부 삭제 후 재삽입하고, 추적이 안 되고, 조회도 불편하다. **일대다 엔티티로 승격하라.**

**여기서 한 것**: 둘 다 아니고 **jsonb 한 컬럼**이다.

```java
@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "footprint_local_m", columnDefinition = "jsonb")
private List<LocalPoint> footprintLocalM;
```

이렇게 든 값이 5개다.

| 엔티티.필드 | 내용 |
|---|---|
| `Building.footprintLocalM` | 건물 대표 외곽선(좌표 배열) |
| `Floor.footprintLocalM` | 층 외곽선 |
| `Floor.nonWalkablePolygonsLocalM` | 못 걷는 면들(중첩 record) |
| `Store.polygon` | 매장 폴리곤 |
| `Store.searchFacets` | `Map<String, List<String>>` 태그 |
| `Edge.geometry` | 간선 꺾은선 |

**일대다로 안 푼 이유:**

1. **항상 통째로 읽고 통째로 쓴다.** "3번째 꼭짓점"을 조회하거나 검색할 일이 없다.
2. **행 수가 폭발한다.** 매장 1,640개 × 폴리곤 꼭짓점 수십 개 = 수만~수십만 행. 좌표
   순서를 지키려면 `@OrderColumn`까지 필요해진다.
3. **파이썬 스키마가 이미 jsonb다.** 이식이므로 모양을 바꿀 이유가 없다.

`@ElementCollection`도 아닌 이유는, 그건 결국 별도 테이블이라 2번 문제가 그대로 남아서다.

### 딸려 온 함정: Hibernate의 JSON 매퍼는 Spring 것이 아니다

```java
public record NonWalkablePolygon(
        String id, String kind,
        @JsonProperty("polygon_local_m") List<LocalPoint> polygonLocalM) {}
```

`application.yml`의 `jackson.property-naming-strategy: SNAKE_CASE`는 **응답 직렬화에만**
적용된다. `@JdbcTypeCode(SqlTypes.JSON)` 컬럼을 읽는 건 Hibernate가 따로 들고 있는
ObjectMapper라 그 설정이 안 걸린다. 그래서 DB에 든 키(`polygon_local_m`)에 맞춰
`@JsonProperty`를 직접 붙인다.

`LocalPoint`가 `record LocalPoint(double x, double y)`라 문제가 안 되는 것도 같은 이유다 —
필드명이 이미 한 글자라 변환할 게 없다.

## 5. 안 쓴 매핑 기능

| 강의 내용 | 안 쓴 이유 |
|---|---|
| `@GeneratedValue` (IDENTITY/SEQUENCE) | id를 서버가 만들지 않는다 |
| `@Embedded` / `@Embeddable` | 좌표는 jsonb 안에 있고, 밖에 있는 `centroid_x_m`류는 컬럼 이름을 파이썬 스키마에 맞춰야 해서 임베디드로 묶으면 `@AttributeOverride`가 더 늘어난다 |
| `@Enumerated(EnumType.STRING)` | enum을 안 쓴다 → [07](07-자바-문법이-쓰인-자리.md) |
| 상속 매핑 (`@Inheritance`, `@MappedSuperclass`) | 엔티티 간 공통 상위 개념이 없다. `Store`와 `Poi`가 비슷해 보이지만 테이블도 원천도 다르다 |
| `cascade`, `orphanRemoval` | 저장·삭제를 안 한다 |
| `@Version` (낙관적 락) | 동시 수정이 없다 |
| Auditing (`@CreatedDate` 등) | 적재 시각은 파이썬 도구가 관리한다 |
