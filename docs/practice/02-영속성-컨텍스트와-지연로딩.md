# 02. 영속성 컨텍스트와 지연로딩

**대응 강의** — JPA 기본편 `03. 영속성 관리`, `08. 프록시와 연관관계 관리`

## 강의에서 배운 것 중 여기서 **안 쓰이는** 것부터

`src/main/java` 전체에 아래가 한 번도 안 나온다.

```
EntityManager   persist(   merge(   flush(   save(   @Modifying   @Version
```

- **쓰기 지연(write-behind)** — INSERT/UPDATE가 없다.
- **변경 감지(dirty checking)** — 엔티티에 setter가 없고 필드를 바꾸는 코드가 없다.
- **스냅샷 비교** — `readOnly = true`라 Hibernate가 스냅샷을 아예 안 뜬다.
- **`merge`, 준영속(detached) 다루기** — 준영속 엔티티를 다시 붙이는 흐름이 없다.

강의 03장 분량의 절반이 여기서는 "해당 없음"이다. 대신 **남은 절반이 전부**다.

## 실제로 일하는 것 1 — 1차 캐시

> 같은 트랜잭션 안에서 같은 식별자를 조회하면 **같은 인스턴스**가 돌아온다.

이 저장소에서 1차 캐시는 "같은 걸 두 번 안 읽는다"보다 **연관을 따라갈 때 쿼리를
안 나가게 한다**는 쪽으로 더 크게 일한다.

### GraphService.toFloorGraph 를 실제로 따라가 보면

```java
public FloorGraphResponse toFloorGraph(Floor floor) {
    List<GraphNodeResponse> nodes = nodeRepository.findByFloorId(floor.getId())...   // ①
    List<GraphEdgeResponse> edges = edgeRepository.findByFloorId(floor.getId())...   // ②
}

private static GraphEdgeResponse toEdge(Edge edge, Map<String, String> nodeFloorIds) {
    String fromNodeId = edge.getFromNode().getId();     // ③
    String toNodeId   = edge.getToNode().getId();
    ...
}
```

③은 간선마다 두 번 실행된다. 층 하나에 간선이 수백 개라면 **여기가 N+1이 터질 자리**다.
그런데 안 터진다.

①에서 그 층의 **모든 노드가 이미 영속성 컨텍스트에 올라와 있어서**다. Hibernate가 ②의
`Edge`를 만들면서 `fromNode`를 채울 때, 영속성 컨텍스트를 먼저 뒤져 이미 있는 인스턴스를
그대로 꽂는다 — 프록시조차 만들지 않는다. 그래서 ③은 그냥 필드 읽기다.

`buildingGraph`도 같은 구조다. 순서가 의도적이다.

```java
List<Floor> floors = floorRepository.findByBuildingId(buildingId);   // 먼저
List<Node>  nodes  = nodeRepository.findByBuildingId(buildingId);    // 그다음
List<Edge>  edges  = ... ;                                           // 마지막
node.getFloor().getId()   // ← floors가 이미 올라와 있어 쿼리가 안 나간다
```

**이 순서를 뒤집으면 N+1이 살아난다.** 코드에는 순서 제약이 명시돼 있지 않으니, 손댈 때
알고 있어야 하는 암묵 규칙이다.

## 실제로 일하는 것 2 — 프록시

### 프록시가 실제로 초기화되는 자리

`FloorMapService.footprintOf`가 유일하게 남은 자리다.

```java
private static List<LocalPoint> footprintOf(Floor floor) {
    if (floor.getFootprintLocalM() != null && !floor.getFootprintLocalM().isEmpty()) {
        return floor.getFootprintLocalM();          // 층 자체 외곽선 — 쿼리 없음
    }
    List<LocalPoint> buildingFootprint = floor.getBuilding().getFootprintLocalM();
    //                                        ↑ 여기서 SELECT * FROM buildings 가 한 번 나간다
}
```

`floor.getBuilding()`은 지연로딩 프록시고, `getFootprintLocalM()`은 **식별자가 아닌 필드**라
프록시가 반드시 초기화된다. 층 하나당 한 번이라 문제가 아니고, 폴백 경로에서만 실행된다.

**p6spy 로그로 직접 확인할 수 있다** — 개발 프로파일에서 층 외곽선이 없는 층을 조회하면
`buildings` 조회가 한 줄 더 찍힌다.

### `getId()`는 정말 쿼리를 안 일으키나 — 조건이 있다

`Node`의 클래스 주석은 이렇게 적혀 있다.

> `floor`는 지연로딩이지만 `getFloor().getId()`는 프록시의 식별자라 쿼리를 일으키지 않는다.

이 명제는 **엔티티의 접근 방식이 프로퍼티 접근일 때** 성립한다. Hibernate가 프록시를 만들
때 "식별자 getter 메서드"를 알고 있어야 그 호출만 가로채 초기화를 건너뛸 수 있기 때문이다.
`@Id`를 getter에 붙이면 그 메서드를 알고, **필드에 붙이면 모른다.**

이 저장소는 애노테이션이 전부 필드에 있으므로 **필드 접근**이다. 즉 정말로 초기화되지 않은
프록시에 `getId()`를 부르면 초기화가 일어날 수 있다.

그런데도 쿼리가 안 나가는 진짜 이유는 위에서 본 **1차 캐시**다. 호출되는 시점에 대상이
이미 영속성 컨텍스트에 있어서 애초에 프록시가 아니다. 주석의 결론("쿼리가 안 나간다")은
맞지만 **근거가 다르고, 근거가 다르면 깨지는 조건도 다르다** — 조회 순서를 바꾸면 깨진다.

> 확인 방법: 개발 프로파일에서 `GET /buildings/{id}/graph`를 부르고 p6spy 로그의 SELECT
> 개수를 센다. 지금은 `buildings`·`floors`·`nodes`·`edges`(intra)·`edges`(transfer)로
> 다섯 줄 안팎이어야 한다.

## `@Transactional(readOnly = true)`

서비스 6개에 전부 붙어 있다. 클래스 레벨 5개(`BuildingService`, `CategoryService`,
`FloorMapService`, `PlaceDetailService`, `GraphService`), 메서드 레벨 2개
(`QuerySearchService`의 공개 메서드 3개, `TileService.renderFloorTile`).

붙는 것이 세 가지다.

1. **성능** — Hibernate가 플러시 모드를 `MANUAL`로 두고 스냅샷을 만들지 않는다. 강의가
   말한 그대로다.
2. **안전장치** — 실수로 쓰기가 섞이면 터진다. 이 서버는 조회만 해야 하므로 유용하다.
3. **가장 중요한 것: 지연로딩이 살아 있는 구간의 경계** — 이 메서드가 끝나면 세션이
   닫히고, 그 뒤로는 프록시를 건드릴 수 없다. 아래 `open-in-view` 이야기와 이어진다.

### `QuerySearchService`만 클래스 레벨이 아닌 이유

이 서비스는 형태소 사전 등록·랭킹 계산 같은 **DB와 무관한 작업이 대부분**이라, 트랜잭션을
클래스 전체로 열면 실제 조회 한 번을 위해 커넥션을 그 계산 시간 내내 붙잡게 된다. 공개
진입점 3개에만 붙였다.

## `open-in-view: false` — 이게 구조를 강제한다

```yaml
spring.jpa.open-in-view: false   # 뷰 렌더 시점까지 세션을 열어두면 지연로딩이 컨트롤러 밖에서 터진다
```

강의(활용2)가 반드시 끄라고 하는 설정이다. 기본값 `true`면 세션이 응답 렌더링까지 열려
있어서, 컨트롤러나 Jackson 직렬화 중에 지연로딩이 일어나고 **DB 커넥션을 응답이 끝날 때까지
붙잡는다.**

끈 결과로 이 저장소에 생긴 규칙이 이거다.

> **서비스는 엔티티를 반환하지 않는다. 무조건 DTO(record)로 바꿔서 나간다.**

실제로 지켜지고 있다.

| 서비스 | 반환 타입 |
|---|---|
| `BuildingService.list()` | `List<BuildingSummaryResponse>` |
| `BuildingService.detail()` | `Optional<BuildingDetailResponse>` |
| `FloorMapService.floorMap()` | `Optional<FloorMapResponse>` |
| `GraphService.buildingGraph()` | `Optional<BuildingGraphResponse>` |
| `PlaceDetailService.detail()` | `Optional<PlaceDetailResponse>` |
| `CategoryService.*` | `List<...Response>` |

엔티티를 그대로 반환했다면 Jackson이 `Store.floor` 프록시를 직렬화하려다
`LazyInitializationException`으로 터진다. **끄면 이 실수가 컴파일이 아니라 첫 요청에서
잡힌다** — 통합 테스트가 실제 HTTP 응답을 검사하는 이유이기도 하다.

부수 효과가 하나 더 있다. `TileService.renderFloorTile`은 캐시 미스일 때만 DB를 읽는데,
`@Transactional`이 메서드 전체에 걸려 있어 **캐시 히트에도 트랜잭션이 열린다.** 실제
비용은 커넥션 획득뿐이라 두고 있지만, 타일 요청이 많아지면 먼저 볼 자리다.

## 정리표

| 강의 03·08장 개념 | 이 저장소 |
|---|---|
| 1차 캐시 | **핵심적으로 쓰인다** — 연관 탐색이 쿼리를 안 내는 근거 |
| 동일성 보장 | 위와 같음 |
| 지연로딩 프록시 | 전 `@ManyToOne`에 적용, 초기화되는 자리는 `FloorMapService.footprintOf` 하나 |
| 플러시 / 쓰기 지연 | 없음 (`readOnly = true`) |
| 변경 감지 | 없음 (setter 없음) |
| 준영속 / `merge` | 없음 |
| `open-in-view` | `false` — 서비스가 DTO를 반환하는 규칙의 근거 |
| 2차 캐시 (`@Cacheable`) | 안 쓴다. 대신 **완성된 산출물**을 Caffeine으로 캐시한다(`TileService`의 타일 바이트) — 엔티티 캐시보다 적중 시 하는 일이 적다 |
