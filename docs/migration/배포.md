# 배포

Cloud Run에 올린다. `main` push마다 [cloudbuild.yaml](../../cloudbuild.yaml)이 이미지를 다시
빌드해 서비스에 밀어 넣는다.

## 왜 이 문서가 있나

**빌드는 저장소에, 서비스 설정은 Cloud Run에 있다.** 둘을 한쪽에 몰면 다른 쪽이 낡는다.
그래서 설정의 단일 출처는 Cloud Run으로 두고, 여기에는 **사람이 읽을 사본**만 적는다.
값을 바꿨으면 이 표도 같이 고친다.

이 분리가 필요한 이유는 파이썬 백엔드에서 이미 겪었다 — 트리거가 콘솔에만 있어 무엇을
빌드하는지 저장소만 봐서는 알 수 없었고, 운영 이미지가 두 벌인 채로 며칠 갔다.

## 지금 배포된 것

| 항목 | 값 |
|---|---|
| 서비스 | `navigation-api-spring` |
| 프로젝트 | `navigation-demo-2026` |
| 리전 | `asia-northeast3` (서울) |
| 메모리 | 1 GiB — 파이썬은 임베딩 모델 때문에 2 GiB였다 |
| CPU | 1 |
| 인스턴스 | 최소 0, **최대 5** (아래 「연결 수」) |
| 인증 | 없음(`--allow-unauthenticated`, 데모 공개) |
| DB | Supabase PostgreSQL 17 (Seoul, `ap-northeast-2`) |

## 환경변수

| 이름 | 값 | 왜 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | `prod` | **빠뜨리면 CORS가 개발 규칙으로 뜬다.** `CorsConfig`가 이 프로파일로 갈린다 |
| `SPRING_SQL_INIT_MODE` | `never` | **빠뜨리면 데모 시드 9건이 실데이터 위로 덮어쓰기를 시도한다.** `application.yml` 기본값이 `always`다 |
| `SPRING_DATASOURCE_URL` | Supabase **Session pooler** 문자열 | Direct connection은 IPv6라 Cloud Run 이그레스(IPv4)에서 안 붙는다 |
| `SPRING_DATASOURCE_USERNAME` | `postgres.<project-ref>` | pooler는 유저명에 프로젝트 ref가 붙는다. 빼면 인증 실패 |
| `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE` | `2` | 아래 「연결 수」 |

`SPRING_DATASOURCE_PASSWORD`는 환경변수가 아니라 **Secret Manager**에서 온다.

```bash
--set-secrets "SPRING_DATASOURCE_PASSWORD=supabase-db-password:latest"
```

평문으로 두면 개정 YAML과 `gcloud run services describe`에 그대로 찍힌다. `:latest`라
비밀번호를 돌릴 때는 새 버전만 추가하면 다음 기동부터 적용된다 — 반대로 잘못된 버전을
넣으면 재배포 없이 다음 콜드 스타트가 깨진다.

## 연결 수

**Supabase Session pooler는 이 등급에서 클라이언트 15개가 상한이다.** 넘기면 기동이
이렇게 실패한다.

```
FATAL: (EMAXCONNSESSION) max clients reached in session mode
       - max clients are limited to pool_size: 15
```

상한은 프로젝트 전체 합이다. 다음을 모두 더해서 센다.

- Cloud Run 인스턴스 수 × 풀 크기
- 기동 때 Flyway가 따로 잡는 1개
- 로컬 개발에서 붙어 있는 것
- **배포 중에는 구·신 revision이 잠시 함께 살아 두 배가 된다**

그래서 `최대 5 × 풀 2 = 10`으로 잡았다. 트래픽이 0.3 req/s라 인스턴스 5개면 넉넉하다.
처리량이 정말 필요해지면 Transaction pooler(6543)가 상한이 훨씬 크지만, Flyway가 동시
마이그레이션을 막는 데 쓰는 advisory lock이 세션 단위라 트랜잭션 모드에서는 걸리지 않는다.

## 수동 배포

트리거 없이 올릴 때. `--source`는 저장소 루트의 `Dockerfile`을 쓴다.

```bash
gcloud run deploy navigation-api-spring --source . \
  --region asia-northeast3 --allow-unauthenticated \
  --memory 1Gi --cpu 1 --min-instances 0 --max-instances 5 --port 8080 \
  --set-env-vars "^@^SPRING_PROFILES_ACTIVE=prod@SPRING_SQL_INIT_MODE=never@..." \
  --set-secrets "SPRING_DATASOURCE_PASSWORD=supabase-db-password:latest"
```

구분자를 `^@^`로 바꾸는 이유: 접속 문자열에 쉼표가 들어갈 수 있는데 기본 구분자가 쉼표다.

## 컷오버

앱이 보는 주소는 파이썬 서비스의 것이고, **클라이언트 매니페스트에 딥링크 호스트로
박혀 있다**(`android:host="navigation-api-...run.app"`). 주소가 바뀌면 이미 설치된 앱의
공유 링크가 통째로 깨진다.

그래서 컷오버는 새 URL로 옮기는 것이 아니라 **같은 서비스의 이미지를 바꾸는 것**이다.

```bash
gcloud run services update navigation-api \
  --image=<검증 끝난 스프링 이미지> --region=asia-northeast3
```

바꾸기 전에 서비스 설정(환경변수·시크릿)을 위 표대로 옮겨 놓아야 한다 — 파이썬 서비스에는
`NAV_*` 환경변수가 붙어 있고 스프링은 그것들을 읽지 않는다.

## 검증

배포 후 파이썬과 응답이 같은지는 [tools/diff_contract.py](../../tools/diff_contract.py)가
확인한다.

```bash
python tools/diff_contract.py <파이썬 URL> <스프링 URL>
```
