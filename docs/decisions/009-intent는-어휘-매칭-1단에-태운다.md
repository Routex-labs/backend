# 009. intent는 별도 단계가 아니라 어휘 매칭 1단에 태운다

## 결정

`search_facets.intents`는 이름·카테고리·동의어와 **같은 1단 어휘 매칭**에서 함께 걸린다.
intent 전용 분류 단계도, 전용 가중치 축도 두지 않는다. 랭킹에서 intent 정확 일치는
카테고리와 **같은 tier 1**이다(`QueryRanking.tier`).

## 왜 카테고리와 같은 tier인가

intent는 "사용자가 치는 말"이고(신발·밥집) 분류 라벨은 운영자가 쓰는 말이라(슈즈·레스토랑)
둘이 어긋나는 게 정상이다. 어느 쪽으로 걸렸는지는 매칭 경로일 뿐 **신뢰도 차이가 아니다**.
어떤 매장이 신발을 파는지는 사람이 검수한 태그로 `search_facets`에 이미 구워져 있다.

## 질의가 가리킨 intent는 되묻지 않는다

clarify 선택지를 만들 때 질의어가 이미 가리킨 intent 값은 뺀다. 방금 친 말을 되돌려주는 건
질문이 아니다(`QuerySearchService.pickQuestion`). 질문 축이 `intents`로 뽑혀도 질의가 가리킨
값을 **덮지 않고 머지**한다 — 덮으면 사용자가 친 근거가 응답에서 사라진다.

한 건으로 확정돼도 intent로 걸린 것이면 `basis`에 근거를 남긴다. 확정 여부와 근거 표시는
별개다.

## 버린 안

**intent 분류기(모델·룰)를 앞단에 둔다** — 질의를 먼저 의도로 접고 그 다음 검색하는 구조다.
단계가 하나 늘고, 오분류가 나면 검색이 아예 다른 곳을 판다. 지금 분포에서 값을 못 한다.

**intent에 별도 가중치 축을 준다** — 튜닝할 손잡이가 하나 더 생기는데 그걸 맞출 근거 데이터가
없다. tier 두 단계로 충분히 갈린다.

**2차 임베딩 검색 이식** — 배포된 파이썬 실측상 `스타벅스`·`신발`·`밥집`은 전부 1단에서
풀렸다. `생일선물 살만한 곳` 류만 `semantic`으로 갔다. 자세한 근거는 `docs/README.md`.

## 다시 볼 조건

경량 매칭이 놓친 질의를 로그로 남기고 있다(커밋 `a663458`). **한 주치 숫자를 보고** 2차가
값을 하는지 판단한다. 그때 임베딩을 얹는다면 intent는 지금 자리(1단)에 그대로 두고 2차를
뒤에 붙인다 — 1단을 건드릴 이유는 아니다.
