# 006. 상세 섹션 순서를 서버가 고정한다

## 결정

섹션 순서는 오버레이(사람이 쓴 JSON)가 준 순서가 아니라 서버가 고정한다.

```
사진 → 공지 → 영업시간 → 연락처 → 태그 → 소개 → 메뉴 → 상세값 → 운영정보 → 링크 → 사업자정보 → 지도
```

## 왜 고정하나

오버레이 순서를 따르면 매장마다 순서가 달라진다. 그러면 사용자가 같은 정보를 같은 자리에서
찾지 못한다. 작성자가 순서를 신경 쓸 필요도 없어진다.

## 왜 이 순서인가

- **사진이 맨 위** — 사진으로 매장을 알아본 다음 무슨 곳인지 읽는다.
- **영업시간이 소개·메뉴보다 위** — 상세를 연 사람이 가장 먼저 정하는 것은 "지금 갈 수 있나"이고,
  그 판단이 무슨 매장인지 읽는 것보다 앞선다.
- **연락처가 영업시간 바로 아래** — "지금 여나"와 "물어볼 수 있나"는 같은 판단의 앞뒤다.
  둘 다 무슨 매장인지 읽기 전에 정하는 것이라 소개보다 위에 둔다.
- **사업자정보(주소)가 맨 아래** — 건물 안에서 길을 찾는 사용자에게 건물 주소는 이미 아는
  정보다. 위쪽 자리를 쓸 값어치가 없다.
- **링크는 운영정보 아래** — 매장을 고르는 데 쓰는 값이 아니라, 고른 뒤에 더 알아보려는
  사람이 찾는 자리다.

## 비어 있는 섹션은 만들지 않는다

값이 없으면 섹션 자체를 넣지 않고, 선택 키는 값이 있을 때만 싣는다. 빈 값이 실려 나가면
클라이언트가 "있는데 비었다"와 "없다"를 구분하는 분기를 갖게 되고, 그 분기가 카드마다 다른
높이로 새어 나온다. `badges`처럼 문자열 배열인 키는 빈 배열도 싣지 않는다 — 응답에
`"badges": []`가 316줄 붙으면 그만큼이 전송 낭비다.

## 낡는 값은 구조체로만 나간다

오버레이 스키마는 `keyValue`·`businessInfo`에 "영업시간"·"전화번호" 같은 라벨을 금지한다.
출처가 없어 확인할 방법이 없고, 시간이 지나면 조용히 거짓이 되기 때문이다.

그렇다고 그 값들을 못 싣게 두면 정작 사용자가 가장 먼저 찾는 둘이 빠진다. 그래서 금지를
푸는 대신 **옆에 확인되는 길을 냈다** — `hours`와 `contact`는 자유 문자열이 아니라 구조체이고
`source`·`confirmed_at`이 필수다. 셋 중 하나라도 없으면 섹션을 만들지 않는다.

`demo_allowlist`를 걸지 않는 이유도 같다. 허용 목록은 무엇이 들어올지 모르는 자유 문자열을
가두는 장치인데, 이 둘은 키가 고정되어 있어 가둘 것이 없다.

## 영업시간은 판정을 만들지 않는다

서버가 "영업 중"을 계산해 넣으면 그 값은 응답을 만든 순간부터 틀리기 시작하고, ETag 캐시가
걸려 있어 더 오래 살아남는다. 서버가 내려보내는 것은 **규칙뿐**이고 지금 시각과의 비교는
화면이 한다.

요일 키가 하나라도 없으면 섹션 자체를 만들지 않는다. 검증 스크립트가 시드 단계에서 막지만,
그 검사를 우회한 데이터가 들어와도 화면에 "모르는 요일 = 휴무"가 뜨지 않게 하는 두 번째 문이다.

검증 기준은 `PlaceDetailControllerTest`가 단일 출처다.
